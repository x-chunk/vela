## R-001 [severity: high] Ошибка скачивания после redirect раскрывает рабочий presigned URL

- Where: `internal/server/deliver.go:154`, `internal/r2/r2.go:305`; взаимодействие с `client/client.go:288`, `client/client.go:100`.
- Problem: новый режим `redirect` направляет в R2 и API-скачивания, которыми пользуются Go-клиент и CLI. При сетевой ошибке на втором HTTP-запросе `http.Client.Do` возвращает `*url.Error`, содержащий полный адрес presigned GET с `X-Amz-Signature` и остальными параметрами авторизации. Существующий `client.attempt` печатает эту ошибку без очистки в HTTP trace и сохраняет в `NetworkError`, чей `Error()` также возвращает полный текст. Поэтому обычная ошибка DNS/TLS/соединения после 302 выводит действующий доступ к приватному файлу в stderr, verbose-журнал или JSON ошибки CLI. Редактирование ошибок внутри `internal/r2` не помогает: сбой происходит в HTTP-клиенте пользователя. Нарушены запрет журналирования подписей и требование трассировки без секретов из SPEC §12.3 и §13.
- Reproduction: получить настоящий 302 от тестового Vela в режиме R2 redirect; в `RoundTripper` клиента вернуть искусственную сетевую ошибку для запроса с `X-Amz-Signature`. Вызов `client.Download` с `WithTrace` и без повторов подтвердил `presigned signature in returned error=true and trace=true`. Для воспроизведения не нужны реальные Cloudflare credentials или вывод значения подписи.
- Suggestion: очистить URL и query во всех печатаемых транспортных ошибках клиента до trace и формирования публичной ошибки, сохранив возможность `errors.Is`/`errors.As` для исходной причины. Добавить клиентский/CLI-тест ошибки после presigned redirect, проверяющий обычный, verbose и JSON-вывод.
- Status: fixed (23f9d9e)
- Resolution: Диагностика транспорта и NetworkError скрывают исходный текст ошибки и URL; unwrap сохраняет исходную причину. Добавлены тесты ошибки после redirect и обычного/verbose/JSON-вывода CLI.

## R-002 [severity: high] Redirect нарушает If-Range и If-Match, вплоть до повреждения возобновляемой загрузки

- Where: `internal/server/deliver.go:115`, `internal/server/deliver.go:126`, `internal/server/deliver.go:147`, `internal/r2/r2.go:305`.
- Problem: Go проверяет условия относительно Vela ETag `"sha256:..."`, но затем возвращает 302. Клиент переносит исходные условные заголовки на запрос к S3, где другой ETag и другой набор поддерживаемых условий. При несовпавшем `If-Range` Vela правильно сбрасывает только локальную переменную `rangeHeader`, однако это никак не меняет `Range` в перенаправленном клиентском запросе. MinIO отдаёт диапазон новой версии с 206 вместо требуемого полного ответа 200. Клиент, возобновляющий скачивание старой версии, может дописать новые байты к старому файлу. Обратная проблема: совпавший с Vela `If-Match` проходит первую проверку, затем S3 отвечает 412, сравнив SHA-256 ETag с собственным валидатором. Это технический дефект обработки HTTP, а не неизбежная потеря эффективности кэширования при redirect. Поддержка S3-условий `If-Match` и отсутствие `If-Range` в перечне R2 GetObject также отражены в [матрице совместимости Cloudflare](https://developers.cloudflare.com/r2/api/s3/api/).
- Reproduction: на MinIO загрузить публичный файл `0123456789`, включить redirect и пройти всю цепочку стандартным `http.Client` (убрав Authorization на переходе). `If-Match: "sha256:<действительный хэш>"` завершился **412**. `Range: bytes=0-2` вместе с `If-Range: "old-etag"` завершился **206**, тело длиной **3**, хотя Vela уже решила вернуть полный файл. В proxy эти решения исполняются локально и не теряются.
- Suggestion: использовать proxy для запросов с условиями, семантику которых нельзя сохранить через внешний redirect; как минимум для `If-Match` и `If-Range`. Проверять конечный статус и тело после перехода, а не только заголовки 302. Добавить сценарий возобновления после перезаписи объекта.
- Status: fixed (d2fba1f)
- Resolution: Условные запросы в режиме redirect обслуживаются через proxy. MinIO-тест проходит конечные статусы и тела для public/API/signed routes, включая If-Match и возобновление после перезаписи.

## R-003 [severity: medium] Go-клиент переносит API-ключ Vela на S3 endpoint с тем же hostname или поддоменом

- Where: `internal/server/deliver.go:159`; взаимодействие с `client/client.go:76`, `client/client.go:283`, `client/client.go:288` и переопределяемым `VELA_R2_ENDPOINT`.
- Problem: API download теперь может перейти на другой сервис, но клиент использует стандартную политику redirect Go. Она сохраняет `Authorization` при том же hostname, в том числе при другом порте, а также при переходе на поддомен исходного хоста. Например, Vela на `127.0.0.1:8080` и поддерживаемый S3 endpoint на `127.0.0.1:9000` получают на втором запросе одновременно presigned query и `Authorization: Bearer <vela-key>`. Это передаёт полномочия Vela сервису хранения без необходимости; MinIO дополнительно отклоняет сочетание способов авторизации с 400, поэтому `vela get/cat` не работают в такой конфигурации redirect. Для обычной пары `store.xchunk.org` → `*.r2.cloudflarestorage.com` hostname различается и этот конкретный дефект не проявляется.
- Reproduction: штатный `client.Download` против локальных Vela и MinIO на разных портах одного hostname вернул `invalid_request: 400 Bad Request`. Дополнительный локальный перехват следующего запроса внутри `RoundTripper`, до любой отправки в S3, подтвердил `Vela API key forwarded=true`. В проверке использован только ключ, созданный тестом во временной SQLite.
- Suggestion: явно удалять Vela Authorization при переходе на presigned delivery URL. Не считать совпадение hostname достаточным основанием доверять другому origin или сервису. Сохранить поддержку пользовательского HTTP-клиента, но обеспечить очистку авторизации и в этом случае. Добавить тест redirect на другой порт и на поддомен с перехватом исходящего заголовка.
- Status: fixed (1e286b8)
- Resolution: HTTP-клиент копируется; Authorization и Referer удаляются на каждом redirect до и после пользовательского callback. Проверены другой порт, поддомен, повторный redirect и штатное скачивание с MinIO.

## R-004 [severity: medium] Сброс Content-Type держит SQLite write transaction во время сетевого чтения R2

- Where: `internal/service/objects.go:509`, `internal/service/objects.go:547`, `internal/service/objects.go:570`; `internal/r2/r2.go:185`.
- Problem: `PATCH {"content_type":null}` вызывает `sniffBlob` внутри `store.Update`. После добавления R2 это уже сетевой GetObject и чтение его тела под `BEGIN IMMEDIATE`, а не короткое чтение локального файла. Единственное writer-соединение и межпроцессная блокировка SQLite остаются заняты на всё время DNS/соединения, SDK retries и чтения первых 512 байт. При задержке или зависании R2 одновременно блокируются несвязанные изменения объектов, отзыв ключей, продление служебных lease и другие записи. `ResponseHeaderTimeout` ограничивает ожидание заголовков, но не чтение тела; отдельного срока на sniff нет. Для вызова достаточно `rw`-ключа на один объект, а блокируется запись во всё хранилище.
- Reproduction: после начала `Open` в `sniffBlob` приостановить backend read, затем параллельно вызвать `CreateKey` с отдельным контекстом на 200 мс. Получено `begin transaction: context deadline exceeded`; после отмены PATCH writer освобождается. Проверка выполнена с реальной SQLite и подменой только блокирующего чтения backend.
- Suggestion: прочитать необходимые байты до write transaction, затем внутри короткой транзакции повторно проверить blob ID/revision и применить изменение к той же версии либо повторить чтение. Задать ограниченный контекст для небольшого служебного sniff, не вводя общий таймаут на загрузки больших файлов. Добавить проверку, что задержка R2 не блокирует несвязанную запись.
- Status: fixed (8a2538a)
- Resolution: Sniff выполняется до write transaction, с контекстом до 10 секунд. Транзакция сверяет ID/blob/revision и повторяет чтение при изменении. Тесты проверяют независимую запись, конкурентную перезапись, If-Match и отмену чтения тела.

## R-005 [severity: medium] Заявленная граница памяти multipart занижена минимум на одну часть на загрузку

- Where: `internal/r2/r2.go:60`, `internal/r2/r2.go:84`, `README.md:158`; та же формула в `docs/SPEC-storage.md:277` и SPEC §21.
- Problem: закреплённый `feature/s3/manager v1.23.14` в `uploader.nextReader` читает первую часть через отдельный `io.ReadAll`, вне `partPool`. Сам pool получает ёмкость `Concurrency + 1`. Пока первые HTTP-запросы частей не завершены, одновременно существуют первая часть и все буферы pool — до `Concurrency + 2` частей, плюс избыточная capacity и временные аллокации `io.ReadAll`. Следовательно, формула `partSize × (concurrency + 1) × maxConcurrentUploads` и обещание 96 MiB для настроек по умолчанию неверны: только полезные данные частей могут занимать **128 MiB** при четырёх загрузках. На малом VPS выбор допустимого параллелизма по опубликованной оценке может привести к OOM. Это не обычные накладные расходы Go/TLS: пропущен отдельный буфер содержимого SDK.
- Reproduction: локальный S3 HTTP stub успешно создаёт multipart, но удерживает ответы всех UploadPart. Генерирующий reader без собственного большого буфера фиксирует объём прочитанного SDK. При `PartSize=8 MiB`, `Concurrency=2` до освобождения запросов потреблено **32 MiB**, тогда как заявленная граница на одну загрузку — **24 MiB**. Механизм дополнительно проверен в исходниках закреплённого SDK: `upload.go`, `init`/`nextReader` и `pool.go`.
- Suggestion: скорректировать расчёт лимита и документацию под фактический SDK либо изменить управление буферами так, чтобы обещанная граница действительно соблюдалась. Включить первую часть и рост `io.ReadAll` в оценку; добавить тест с приостановленными part-запросами и несколькими одновременными загрузками.
- Status: fixed (d50ef31)
- Resolution: Исправлены комментарии и обе спецификации/README: полезные данные до (concurrency + 2) частей (128 MiB по умолчанию); отдельный запас на рост первой части и GC. Тест с удержанием ответов UploadPart проверяет одну и четыре одновременные загрузки.

## R-006 [severity: medium] Допустимая конфигурация размера может гарантированно падать только после загрузки 10 000 частей

- Where: `internal/r2/r2.go:61`, `internal/r2/r2.go:90`, `internal/r2/r2.go:99`; `internal/config/storage.go:108`, `internal/velad/storage.go:128`.
- Problem: размер части фиксирован, `SizeHint` используется только для сравнения с `MaxSize`, а SDK всегда получает `cancelOnReadError`/`content.Stream`, не реализующий `io.Seeker`. Поэтому менеджер не узнаёт размер и не применяет свою автоматическую корректировку PartSize. При этом конфиг не сверяет `VELA_MAX_UPLOAD` с пределом в 10 000 частей. Например, `VELA_MAX_UPLOAD=100GiB` с default `VELA_R2_PART_SIZE=8MiB` принимается и объявляется клиентам, но файл свыше **78.125 GiB** не может быть загружен: менеджер достигает предела частей, абортит загрузку и возвращает внутреннюю ошибку после передачи почти всего этого объёма. Аналогично падает миграция большого FS-блоба в R2, хотя мигратор передаёт точный `SizeHint`. Ограничение 10 000 частей документировано у [Cloudflare R2](https://developers.cloudflare.com/r2/platform/limits/); проблема в несогласованной валидации и позднем отказе, а не в самом ограничении провайдера.
- Reproduction: граница и отсутствие автоматического изменения размера подтверждены в `initSize` и `shouldContinue` закреплённого SDK. Без передачи десятков гигабайт выполнена масштабированная проба: у того же менеджера лимит частей уменьшен до двух, размер части оставлен 8 MiB; файл 17 MiB с `MaxSize=32 MiB` и известным `SizeHint=17 MiB` завершается `upload blob: backend request failed`. Полноразмерная загрузка 100 GiB не выполнялась.
- Suggestion: согласовать максимальный размер с количеством частей при проверке конфигурации и до начала миграции. Либо рассчитывать подходящий PartSize с учётом известного размера/максимума и общего бюджета памяти, либо заранее отклонять неподдерживаемый размер с понятной диагностикой. Не полагаться на автоматическое изменение размера в SDK для обёрнутого потокового reader.
- Status: fixed (9ea007f)
- Resolution: Конфигурация сверяет upload/create limits с partSize × 10000. Put отклоняет неподдерживаемый лимит до чтения/HTTP; миграция предварительно проверяет все размеры, включая dry-run. Добавлены тесты границ и раннего отказа.

## R-007 [severity: low] Команды из нового README не соответствуют CLI

- Where: `README.md:272`, `README.md:292`, `README.md:293`, `README.md:294`.
- Problem: примеры загрузки и создания используют `--visibility public/private`, но команды `put` и `new` регистрируют только отдельные `--public`, `--unlisted`, `--private`. Пример создания подписанной ссылки вызывает `vela link`, хотя команда называется `vela share` и alias `link` отсутствует. Поэтому документированный сценарий не выполняется даже с корректно настроенным сервером. Это ошибки исполняемых инструкций, а не замечание к полноте или продуктовой структуре руководства.
- Reproduction: запуск соответствующих команд текущего CLI возвращает `unknown flag: --visibility` и `unknown command "link" for "vela"`, код выхода CLI 2, до обращения к серверу.
- Suggestion: заменить флаги в примерах на `--public`/`--private`, а `vela link` — на `vela share`; сверить остальные исполняемые примеры с текущими command/flag definitions.
- Status: fixed (6f30760)
- Resolution: Примеры используют --public/--private и vela share; добавлен обязательный --name в пример scoped key. Login и все 13 CLI-команд README выполнены на собранных бинарниках против временного velad; содержимое скачанного файла сверено.
