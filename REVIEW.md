## R-001 [severity: high] Успешный online backup может содержать объекты без содержимого

- Where: `internal/velad/maintenance.go:69`, `internal/velad/maintenance.go:91`, `internal/velad/maintenance.go:97`; `internal/service/objects.go:433`.
- Problem: После `VACUUM INTO` резервное копирование берёт список blob ID из снимка, но читает файлы из живого хранилища без защиты от удаления. Перезапись объекта или purge между этими шагами удаляет нужный снимку blob. Обработка `fs.ErrNotExist` лишь увеличивает `missing` и возвращает успех; запись в снимке остаётся. Предупреждение «their objects were deleted too» неверно применительно к снимку и даже к живому объекту при overwrite. Нарушается обещание consistent backup (§13, §16).
- Verification: Между завершением Snapshot и чтением его blob выполнен настоящий overwrite через клиент. Результат backup: `err=nil, missing=1`; снимок сохраняет старый blob ID, соответствующего файла в копии нет.
- Suggestion: Согласовать backup с физическим удалением файлов: закреплять все blob снимка или удерживать общую межпроцессную защиту до создания hard links / открытия источников. Любой недостающий blob должен делать backup неуспешным. Не «чинить» снимок удалением записей: это потеряет данные, которые backup обязан был сохранить.
- Regression: Параллельные overwrite, purge и janitor между snapshot и link/copy; восстановление копии с проверкой каждого объекта и SHA-256.
- Status: fixed

## R-002 [severity: high] Удаление старого blob опережает гарантированную фиксацию изменения БД

- Where: `internal/store/store.go:67`, `internal/store/store.go:129`; `internal/service/objects.go:433`; `internal/service/trash.go:111`, `internal/service/trash.go:264`, `internal/service/trash.go:321`.
- Problem: WAL с `synchronous=NORMAL` допускает откат уже завершённой транзакции при сбое ОС/питания. После возврата Commit сервис немедленно удаляет старый blob. Удаление файла может сохраниться на носителе, а обновление SQLite — нет: после запуска старая строка снова ссылается на уже отсутствующее содержимое. Это потеря ранее сохранённого файла, а не только последней операции. Сам выбор NORMAL предусмотрен спецификацией; ошибка — несогласованная с его гарантиями физическая очистка.
- Verification: Анализ порядка операций и [официальных гарантий SQLite](https://sqlite.org/pragma.html#pragma_synchronous). Аварийное отключение не воспроизводилось.
- Suggestion: Удалять заменённые/очищенные blob только после гарантированной durable-фиксации исключающих их ссылок либо через отложенную очередь с проверяемым барьером durability. Одной успешной транзакции при NORMAL недостаточно.
- Regression: Fault-injection между commit, синхронизацией WAL и unlink; после восстановления каждая строка objects/trash должна иметь доступный blob.
- Status: fixed

## R-003 [severity: high] Commit blob не синхронизирует создание родительских shard-каталогов

- Where: `internal/blob/blob.go:158`, `internal/blob/blob.go:162`, `internal/blob/blob.go:175`, `internal/blob/blob.go:188`.
- Problem: При первом файле в shard создаются `blobs/ab` и `blobs/ab/cd`, но после rename синхронизируется только конечный `cd`. Записи о новых каталогах в `blobs` и `ab` не fsync-ятся. Файл может быть признан сохранённым и записан в БД, хотя после сбоя один из родителей исчезнет. Кроме того, chmod с 0600 на 0644 выполняется после последнего Sync файла; сохранность окончательных прав тоже не обеспечена. Комментарий Commit обещает более сильную гарантию, чем реализация.
- Verification: Анализ кода и [fsync(2) из Linux man-pages](https://raw.githubusercontent.com/mkerrisk/man-pages/master/man2/fsync.2): синхронизация inode не заменяет синхронизацию записи в содержащем каталоге. Power-loss тест не проводился.
- Suggestion: Синхронизировать каждую вновь созданную связь каталогов и выполнять окончательный Sync файла после установки метаданных. Учесть создание корневых директорий при первом запуске.
- Regression: Fault-injection первого upload в новый shard, включая сбой после chmod и после каждого mkdir/rename.
- Status: fixed

## R-004 [severity: high] Снимок БД временно создаётся с доступными другим пользователям правами

- Where: `internal/store/store.go:137`; `internal/velad/maintenance.go:58`, `internal/velad/maintenance.go:65`.
- Problem: Snapshot вызывает `VACUUM INTO` и только после его завершения chmod 0600. SQLite создаёт целевой файл с 0644 при обычном umask 022. Backup разрешает существующий пустой каталог и не меняет его права: `MkdirAll(dest, 0700)` для существующего 0755 ничего не делает. В таком каталоге локальный пользователь может прочитать снимок до chmod, включая секреты HMAC-подписи; при ошибке/остановке до chmod доступный файл может остаться.
- Verification: На используемом драйвере и umask 022 после самой операции `VACUUM INTO` права снимка — 0644. Окно до chmod и сохранение режима существующего каталога подтверждены кодом.
- Suggestion: Создавать пустой целевой файл сразу с 0600 до VACUUM INTO и обеспечивать защищённый staging-каталог до начала записи секретов. Права должны быть безопасными с первого байта, включая аварийные пути.
- Regression: Backup в заранее созданный 0755-каталог, наблюдение прав во время копирования, ошибка/прерывание VACUUM.
- Status: fixed

## R-007 [severity: high] Query string подписанных ссылок попадает в два журнала nginx

- Where: `deploy/nginx/store.xchunk.org.conf:28`, `deploy/nginx/store.xchunk.org.conf:56`; `deploy/nginx/vela.conf:36`.
- Problem: Безопасный `access_log ... vela_noquery` задан только в TLS server. HTTP server с redirect наследует обычный access log, содержащий `$request` вместе с query. Кроме того, безопасный log_format никак не меняет nginx error log: например, при отказе соединения с upstream он пишет полную исходную строку запроса, включая `sig`. Второй путь действует и для запросов к HTTPS. Это нарушает инвариант отсутствия подписей и query в логах (§7.3, §8, AGENTS.md).
- Verification: Реальный nginx с HTTP server из референса записал контрольную подпись запроса с ответом 301. Для proxy server с включённым `vela_noquery` отказ upstream дал строку `[error]` с контрольной подписью. В тесте использовались искусственные значения, а не рабочие секреты.
- Suggestion: Применить безопасный access log ко всем server-блокам. Отдельно решить редактирование/исключение request URI в error-log трактах; изменение access log не устраняет вторую утечку. Проверять фактические логи, а не только конфигурацию формата.
- Regression: HTTP redirect, недоступный velad, ошибка чтения blob и обычный HTTPS-запрос: ни один журнал не содержит тестовый sig/query.
- Status: fixed

- Suggestion: Устанавливать и проверять ограниченный DACL платформенным кодом; при невозможности обеспечить приватность возвращать понятную ошибку.

## R-013 [severity: medium] ETag nginx совпадает у разного содержимого после overwrite

- Where: `internal/server/deliver.go:74`; `deploy/nginx/vela.conf:48`.
- Problem: В accel mode используется стандартный файловый ETag nginx, зависящий от размера и mtime с точностью до секунды. Два разных blob одинакового размера, загруженные в одну секунду под один логический URL, получают один валидатор. Клиент с предыдущим If-None-Match получает 304 и сохраняет старые байты. Ошибка переживает разрешённые пять минут cache freshness: последующие ревалидации тоже подтверждают старое содержимое. If-Range также может ошибочно принять старый валидатор.
- Verification: Реальный nginx: AAAA заменено на BBBB, обоим blob выставлен mtime в одной секунде. Запрос с прежним ETag получил 304; ETag совпал. Выставление mtime только делает обычную секундную коллизию детерминированной.
- Suggestion: Обеспечить валидатор, отражающий содержимое/идентичность blob и учитываемый nginx при условных запросах. В direct mode уже используется SHA-256; простого изменения заголовка после принятия nginx решения о 304 недостаточно.

## Приоритет исправления и покрытие

Сначала необходимы R-001–R-005 и R-007: они затрагивают сохранность данных и границы доступа. R-006, R-008, R-011–R-017, R-019–R-023 требуют следующей очереди из-за повседневных операций upload/download/backup и возможности ложного успеха. Низкая тяжесть R-030/R-031 не означает, что их следует оставить: это конкретные воспроизведённые ошибки.

Архитектурное разделение server/service/store/blob и wire в целом выдержано; штатный archtest проходит. В проверенных обычных сценариях существующие тесты подтверждают scopes/prefixes, сравнение секретов за постоянное время, атомарность конфликтующих DB-операций, 404 для недоступных публичных объектов, привязку exp к сохранённой ссылке и сохранение identity при move/restore. Это не является доказательством отсутствия иных дефектов.

Качество комментариев в целом соответствует производственному стилю; существенные неточности связаны именно с гарантиями реализации: backup (R-001/R-022), durability Commit (R-003), защита локального пути (R-005), безопасность конфига на Windows (R-010), body idle timeout (R-011), retries (R-019/R-021), эксклюзивность janitor (R-029), временной порядок ULID (R-030). Они указаны вместе с соответствующей ошибкой, без дублирования отдельными stylistic findings.

Наиболее заметные пробелы тестов — конкурентное удаление blob после snapshot/resolve, аварийная фиксация между SQLite и filesystem, симлинки и no-replace при локальной записи, реальные os.File в retries, усечённые успешные ответы, предельные Unicode/JSON/header размеры, output-contract всех CLI-команд и журналы/не-blob ответы nginx. Native Windows ACL и реальный power-loss стенд остаются необходимыми отдельными проверками.
