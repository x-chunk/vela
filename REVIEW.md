## R-008 [severity: medium] Ответ 416 может попасть в кэш и заблокировать обычное скачивание файла

- Where: `internal/server/deliver.go:113`, `internal/server/deliver.go:131–135`.
- Problem: для объектов `public` и `unlisted` обработчик устанавливает `Cache-Control: public, max-age=300` и ETag файла до разбора Range. При ошибке диапазона новый обработчик возвращает 416, сохраняя эти заголовки. До рассматриваемых изменений `http.ServeContent` удалял Cache-Control и ETag в этой ветке. В результате кэширующий посредник может сохранить ошибку под URL файла и возвращать её последующим обычным GET без Range. Для запуска сценария достаточно неавторизованного запроса к доступному публичному URL; файл при этом существует и исправен. Это затрагивает FS direct и общий путь R2: ветка 416 выполняется до выбора proxy/redirect. Явное разрешение кэширования имеет значение и для отрицательных ответов — см. [RFC 9111, §3 и §4](https://www.rfc-editor.org/rfc/rfc9111.html#section-3).
- Reproduction: загрузить публичный `cache.txt` с содержимым `0123456789`; поставить перед Vela отдельный nginx с `proxy_cache`, обычным ключом по URI и передачей `Range`. Запросить `GET /cache.txt` с `Range: bytes=100-`, затем обычный `GET /cache.txt`. На текущем HEAD первый ответ — `416`, `X-Cache: MISS`, `Cache-Control: public, max-age=300`; второй — **`416`, `X-Cache: HIT`, пустое тело**. Та же проба на чистом `3acc1ed` даёт первый 416 без Cache-Control/ETag и второй **200 с исходными десятью байтами**. Проверено на реальном `nginx:1.30-alpine`, без подмены обработчика Vela. Штатный конфиг проекта кэш не включает; необходимое условие — CDN или другой посредник с кэшированием перед сервером.
- Suggestion: для 416 явно выставлять `Cache-Control: no-store` и не оставлять валидатор успешного представления; сохранить обязательный `Content-Range: bytes */<size>`. Добавить проверку, что ошибочный Range не влияет на последующий обычный GET через кэш. При централизации ошибок доставки отдельно учитывать политику кэширования ошибочного ответа.
- Status: fixed (e2e5207)

## R-009 [severity: low] Справка backup описывает R2-бэкап как полный и даёт неполную инструкцию восстановления

- Where: `internal/velad/maintenance.go:124–128`; связанная справка и итоговый вывод — `internal/velad/maintenance.go:31–38`, `internal/velad/maintenance.go:50–55`.
- Problem: новая ветка R2 успешно завершает backup после сохранения SQLite, но `velad backup --help` безусловно обещает копирование каждого блоба, проверку его размера, ошибку при отсутствующем содержимом и восстановление заменой локальных `vela.db` и `blobs/`. Итоговый вывод также не обозначает, что создан только бэкап метаданных. Эти утверждения неверны при R2: содержимое бакета вообще не проверяется и не попадает в результат. Оператор, использующий встроенную справку для резервного копирования и восстановления, получает неполную процедуру и может обнаружить отсутствие содержимого только при восстановлении после утраты бакета. README уже правильно объясняет раздельное резервирование; замечание касается противоречащей ему технической инструкции CLI, а не самого решения сохранять R2 отдельно.
- Reproduction: с одной записью объекта в реальной SQLite выполнить ветку backup с `Kind="r2"`: операция успешна, результат `{objects:1 blobs:0 linked:0 copied:0}`, в каталоге только `vela.db`. Вызов текущего `backup --help` содержит обещание `every blob`, но не упоминает R2 или режим metadata-only. Сценарий проверен отдельной диагностической пробой без обращения к внешнему бакету.
- Suggestion: уточнить встроенную справку для обоих бэкендов: R2 сохраняет только SQLite, `--verify` для него недоступен, а для восстановления нужна согласованная копия бакета. В успешном выводе R2 явно указывать, что содержимое бакета не включено.
- Status: fixed (0f7b6a0)
