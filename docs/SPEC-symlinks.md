# Vela — дополнение к спецификации: символические ссылки (`vela ln`)

> Дополнение к `docs/SPEC.md` и последующим дополнениям (`SPEC-storage.md`, `SPEC-dirs.md`,
> `SPEC-web.md`). Где этот документ противоречит предыдущим, **приоритет у этого документа**.
> Термины MUST / SHOULD / MAY — как в основном SPEC.

---

## 0. TL;DR

- Новый тип объекта — **симлинк** (`kind = "symlink"`): запись по своему пути, которая указывает на
  обычный файл **по его ID**, а не по пути. Своих байтов нет; содержимое, размер, SHA-256 и тип
  берутся у цели в момент запроса.
- Сценарий: оригиналы лежат в одном месте (`originals/…`), а в другом (`sorted/…`) они
  рассортированы, в том числе один файл в нескольких местах. Переименование и перемещение оригинала
  ссылку не ломают, перезапись подхватывается, удаление делает ссылку битой.
- У каждого симлинка **свои метаданные**. При создании они по умолчанию **копируются снимком**
  у источника (title, description, tags, disposition, visibility); явные поля сильнее.
- **Эффективная видимость** = строжайшая из (симлинк, цель). Публичный симлинк на приватный файл → 404.
- Префикс ключа проверяется **и для пути симлинка, и для пути цели** — при создании и при каждом чтении.
- CLI: `vela ln SRC... DST`, `vela ln -r SRC/ DST/`, `-f` для замены или перенаправления.
- Цепочек нет (цель — всегда обычный файл), симлинков на директории нет, режима «по пути» нет.

---

## 1. Решения

| # | Решение |
|---|---|
| P1 | Привязка только по **ID объекта**. Режим «по пути» (`latest → X`) не делается; его можно добавить позже аддитивно. |
| P2 | У каждого симлинка свои метаданные. При создании по умолчанию копируются у источника снимком; `copy_meta: false` (`--no-copy-meta`) — не копировать. Живого наследования нет. |
| P3 | После purge оригинала симлинки **остаются битыми**: видны в `vela ls` как broken, публично 404. Удаляются только явно (`vela rm`, `vela rm --broken`). |
| P4 | Несколько источников (`vela ln a b c dir/`) и рекурсивное создание (`vela ln -r src/ dst/`). |
| P5 | Аналог `ln -s`, но по ID. Жёстких ссылок и `vela cp` нет. |
| D1 | `PUT`/`POST /objects`/`vela put`/`vela new` **на путь симлинка запрещены** (409 `is_symlink`), даже с перезаписью. Записи «сквозь» симлинк нет: вместе с префиксами ключей это был бы путь к эскалации. |
| D2 | `overwrite` на **существующий симлинк** перенаправляет его **на месте** (тот же ID, `revision++`); метаданные сохраняются, если не передан `copy_meta: true` или явные поля. На **обычный файл** — файл уходит в корзину, создаётся новый симлинк. Сохранение ID оставляет рабочими публичный URL и подписанные ссылки. |
| D3 | Источник-симлинк **разыменовывается**: новый симлинк указывает на оригинал. Метаданные копируются **с названного источника** (с симлинка — то, что видит пользователь). |
| D4 | Явный список тегов **заменяет** скопированный (как в `put`). |
| D5 | `expires_at` **не копируется**: это срок жизни записи, а не свойство содержимого. |
| D6 | Для анонимных посетителей симлинк в HTML-индексе выглядит **как обычный файл**; путь цели публично не раскрывается никогда. На страницах web-сессии симлинк помечен флагом `symlink` (синий значок, как остальные флаги сессии); контракт темы расширен аддитивно. |
| D7 | Счётчики «затронуто симлинков» в ответах API считаются **только в пределах префикса ключа** (инвариант 6). |
| D8 | Терминология: в API, коде и CLI всегда **`symlink`**, никогда голое `link` — `links` занято подписанными ссылками. |
| D9 | Для цели в корзине `target.path` — её исходный путь в корзине (если он в префиксе ключа): это подсказка для `vela trash restore`. |
| D10 | Рекурсивное создание ограничено 10 000 объектов за запрос (400 `invalid_request` с подсказкой); у рекурсивного `move` лимита нет, но он ничего не создаёт. |

## 2. Термины

- **Файл** (`kind = "file"`) — обычный объект с блобом.
- **Симлинк** (`kind = "symlink"`) — объект без блоба с `target_id`.
- **Цель** — объект, на который указывает симлинк (всегда `kind = "file"`).
- **Источник** — путь, переданный в `vela ln`; если это симлинк, цель = его цель (D3).
- **Состояние цели** (`target.state`):
  - `ok` — цель жива (в таблице `objects`);
  - `trashed` — цель в корзине (восстановление её «оживит» — ID сохраняется);
  - `gone` — цели нет (purge) **или** она вне префикса ключа запрашивающего (для такого ключа неразличимо).
- **Битый симлинк** — `target.state != ok`.
- **Эффективная видимость** — строжайшая из видимости симлинка и видимости цели
  (`private` > `unlisted` > `public`); для битого симлинка — `private`.

## 3. Семантика

### 3.1 Создание

- Требуется scope `rw`.
- Источник должен существовать в `objects` (не в корзине). Просроченный, но ещё не убранный janitor-ом
  источник допустим — через API он ещё доступен (SPEC §19 п.6).
- Источник — файл или симлинк (D3). Битый симлинк как источник → 404 `not_found`.
- Источник — директория без `recursive` → 400 `invalid_request`.
- Путь симлинка проходит `api.CleanObjectPath` и все правила SPEC §4, включая конфликт файл/директория §4.2.
- Префикс ключа MUST покрывать **путь симлинка и путь цели** (при `recursive` — оба префикса), иначе 403 `forbidden`.
- Симлинк на самого себя невозможен: `overwrite` на путь самой цели → 400 `invalid_request`.
- Занятый путь назначения:
  - без `overwrite` → 409 `already_exists`;
  - с `overwrite`, там симлинк → перенаправление на месте (D2), 200;
  - с `overwrite`, там файл → файл в корзину (как в `move`), новый симлинк, 201.
- Метаданные при **создании**: если `copy_meta` не `false` — копируются `title`, `description`, `tags`,
  `disposition`, `visibility` с источника (D3). Иначе — значения по умолчанию сервера
  (`VELA_DEFAULT_VISIBILITY` и т.п.). Явные поля запроса перекрывают и то и другое. `expires_at` — только явно (D5).
- Метаданные при **перенаправлении** (D2): сохраняются; `copy_meta: true` — перекопировать; явные поля — применить.
- Если сохранённая видимость симлинка мягче видимости цели, создание проходит, а CLI печатает
  предупреждение об эффективной видимости.

### 3.2 Рекурсивное создание

- `source` и `path` — префиксы с `/`. Для каждого объекта под `source` создаётся `path + относительный_путь`.
  Симлинки внутри `source` разыменовываются (D3); битые пропускаются и возвращаются в `skipped` (до 100 путей).
- **Одна транзакция**, как рекурсивный `move`: при занятых путях без `overwrite` → 409 `already_exists`
  с `details.conflicts` (до 100 путей), при конфликте файл/директория → 409 `path_conflict`; ничего не создаётся.
- `skip_symlinks: true` — симлинки внутри `source` не связываются (не разыменовываются и не попадают в `skipped`).
- `skip_conflicts: true` — конфликтные назначения (файл/директория, путь самой цели, занятые без `overwrite`)
  пропускаются, остальное создаётся в той же транзакции; пропущенные возвращаются в `skipped_conflicts`
  (до 100 путей). С `overwrite` занятые пути по-прежнему заменяются.
- Оба поля — только при `recursive`, иначе 400 `invalid_request`. Сервер объявляет их `features.symlink_tree_skip`.
- `path` внутри `source` допустим: объекты под `path` в обход не попадают, поэтому повторный запуск не связывает
  симлинки прошлого запуска уровнем глубже. `path == source` → 400 `invalid_request`.
- Это **снимок**: файлы, появившиеся в `source` позже, автоматически не связываются.
- Политики директорий **не копируются**: это сортировка, а не перенос.
- Не больше 10 000 объектов за запрос (D10).
- `path` не может лежать внутри `source` (400 `invalid_request`).

### 3.3 Чтение и доступ

Резолв всегда одноуровневый: `symlink → target_id → objects` (не `trash`).

| Ситуация | Публичный URL / web-сессия / подписанная ссылка | API (ключ) download | API stat / ls |
|---|---|---|---|
| Цель жива, видимость ок | отдаёт содержимое цели | отдаёт | `target.state = ok` |
| Цель `private`, симлинк `public` | **404** (подписанная ссылка — отдаёт) | отдаёт, если цель в префиксе ключа | ok |
| Цель просрочена, не убрана janitor-ом | **404** | отдаёт (как у файла) | ok, `target.expired = true` |
| Цель в корзине | 404 | 404 | `trashed` |
| Цель удалена навсегда | 404 | 404 | `gone` |
| Цель вне префикса ключа | — | **404** (не 403: не раскрываем) | `gone`, `target.path = null` |
| Сам симлинк `private` / просрочен | 404 | по обычным правилам | по обычным правилам |

- Публичная сторона отдаёт симлинк, только если **эффективная** видимость ≠ `private`, ни симлинк,
  ни цель не просрочены и цель жива. Все отказы — 404 (инвариант 2).
- Web-сессии (инвариант 14): симлинк виден сессии, если сессии виден **сам симлинк** (анонимный вид или
  путь симлинка в префиксе ключа) **и цель** (эффективно не-`private` или путь цели в префиксе ключа).
  Иначе — анонимный ответ, т.е. 404.
- Подписанные ссылки на симлинк: `object_id` = ID симлинка. Порядок проверок SPEC §8.2 сохраняется
  (сначала `exp`, без БД). Дальше — симлинк и цель живы и не просрочены; видимость не важна.
  Битый симлинк → 404. После перенаправления (D2) подписанная ссылка следует за новой целью.

### 3.4 Операции над симлинком

| Операция | Поведение |
|---|---|
| `stat` | данные **самого симлинка** + блок `target` (как `lstat`) |
| download / `cat` / `get` | содержимое цели; имя файла — имя **симлинка** |
| `PATCH` | метаданные симлинка: `title`, `description`, `tags`, `visibility`, `disposition`, `expires_at`. `content_type` → 400 `invalid_request`. Цель через PATCH не меняется. |
| `vis` (в т.ч. `-r`) | меняет видимость самого симлинка |
| `mv` | двигает симлинк, цель не трогается; рекурсивный `move` двигает симлинки вместе с файлами |
| `mv --force` на путь симлинка | симлинк назначения уходит в корзину, как любой объект |
| `rm` | симлинк в корзину; цель не трогается |
| `trash restore` | восстанавливает симлинк (тот же ID); битость пересчитывается при чтении |
| `trash purge` | удаляет строку; в `blob_gc` ничего не ставится |
| upload / create на путь симлинка | 409 `is_symlink` (D1) |
| `share` | подписанная ссылка на симлинк (§3.3) |
| `url` / `open` | публичный URL симлинка; для эффективно `private` — ошибка с подсказкой `share` |
| собственный `expires_at` | janitor отправляет просроченный симлинк в корзину, как файл |

### 3.5 Операции над целью и их эффект на симлинки

| Что сделали с оригиналом | Симлинки |
|---|---|
| Перезапись (тот же ID) | отдают новое содержимое; ETag меняется (новый SHA-256) |
| `meta` / `vis` / `content_type` | метаданные симлинков не меняются (снимок); тип содержимого и ограничение видимости следуют автоматически |
| `mv` / рекурсивный `mv` | работают, `target.path` показывает новый путь |
| `rm` (в корзину) | `trashed`, публично 404; ответ DELETE сообщает `symlinks_affected` |
| `trash restore` (в т.ч. по другому пути) | снова работают (ID сохраняется) |
| `trash purge` / автоочистка корзины | `gone` навсегда (P3); ответ purge сообщает `symlinks_affected` |
| Просрочка по `expires_at` | публично 404 сразу; после janitor — `trashed` |

ULID не переиспользуются, поэтому битый симлинк никогда не «оживёт» на чужом объекте.

### 3.6 Публичная часть и индекс

- Публичный URL симлинка — его собственный путь.
- HTML-индекс и `?format=json`: симлинк — обычная строка файлов (D6). Размер и тип содержимого — от цели;
  `title`, `description`, `tags`, `updated_at` — от симлинка. Показывается, только если **эффективная**
  видимость `public` и симлинк «живой». Unlisted-цель → симлинк не листится, но отдаётся по URL.
- Счётчики и даты директорий, существование публичной директории и редирект на неё учитывают симлинки
  по тем же правилам.
- Политики директорий (`noindex`, `hidden`, index) применяются по пути **симлинка**. Скрытая директория —
  не конфиденциальность (SPEC-dirs): симлинк из видимой директории на файл в скрытой — осознанное
  действие владельца.

### 3.7 Битые симлинки

- Автоматически не удаляются (P3).
- `vela ls -l` помечает их (`broken: trashed` / `broken: gone`), `vela ls --broken [-r] DIR/` — только они.
- `vela rm --broken [-r] DIR/` — найти и отправить в корзину битые симлинки; подтверждение как у `rm -r`.
- `vela stat` битого симлинка печатает подсказку: для `trashed` — `vela trash restore …` (если путь цели
  доступен ключу), для `gone` — `vela rm` или `vela ln -f НОВЫЙ_ИСТОЧНИК ПУТЬ`.

## 4. Контракт API v1 (аддитивно)

Только новые эндпоинты, новые поля ответа, новые необязательные параметры и новый код ошибки для новой
ситуации — **v1 не ломается**, `APIVersion` не меняется. Старые клиенты увидят в листинге объекты,
у которых для битых симлинков `size = 0`, `sha256 = ""`, `content_type = ""` (SPEC §21).

### 4.1 `api.Object` — новые поля

```jsonc
{
  "kind": "symlink",                  // "file" | "symlink"; всегда присутствует
  "effective_visibility": "unlisted", // для файла == visibility
  "target": {                         // null для kind=file
    "id": "01k…",                     // всегда (свойство самого симлинка)
    "path": "originals/a.jpg",        // текущий путь (для trashed — исходный); null при gone или вне префикса
    "state": "ok",                    // ok | trashed | gone
    "visibility": "unlisted",         // null, если цель не жива
    "expired": false
  }
  // size, sha256, content_type — от цели при state=ok; иначе 0 / "" / ""
  // url — по effective_visibility (null, если эффективно private)
}
```

### 4.2 `POST /api/v1/symlinks` — создание и перенаправление

```jsonc
{
  "source": "originals/a.jpg",   // или префикс с "/" при recursive
  "path": "sorted/travel/a.jpg", // или префикс с "/" при recursive
  "recursive": false,
  "overwrite": false,
  "skip_symlinks": false,        // только при recursive, §3.2
  "skip_conflicts": false,       // только при recursive, §3.2
  "copy_meta": null,             // null → true при создании, false при перенаправлении
  "visibility": null,            // все поля ниже необязательны: null/отсутствие = не задано
  "title": null,
  "description": null,
  "tags": null,
  "disposition": null,
  "expires_at": null
}
```

- Одиночный: `201` + `Object` (создан) или `200` + `Object` (перенаправлен на месте).
- Рекурсивный: `200` + `{ "created": n, "replaced": m, "skipped": ["…"], "skipped_conflicts": ["…"] }`.
- Ошибки: `400 invalid_request`, `400 invalid_path`, `403 forbidden`, `404 not_found` (источник),
  `409 already_exists` (+ `details.conflicts` для рекурсивного), `409 path_conflict`.
- Клиент не повторяет запрос автоматически (POST, как `move`).

### 4.3 `GET /api/v1/objects` — новые параметры

- `kind=file|symlink` — фильтр по типу; неизвестное значение → 400.
- `broken=true` — только битые симлинки (подразумевает `kind=symlink`).
- `target=<path>` — симлинки, указывающие на объект по этому пути. Путь цели MUST быть в префиксе ключа;
  результаты ограничены префиксом ключа; несуществующий путь → пустой список.
- `visibility=` фильтрует по **эффективной** видимости.

### 4.4 Изменения существующих ответов

- `DeleteResponse` и `PurgeResponse`: `symlinks_affected` — число живых симлинков (в префиксе ключа),
  ставших битыми из-за операции.
- `api.Info`: `features: { "symlinks": true, "symlink_tree_skip": true }`. CLI по нему понимает, что сервер
  поддерживает симлинки и поля `skip_*` рекурсивного создания.

### 4.5 Новый код ошибки

- `is_symlink` (409): запись содержимого в путь, где лежит симлинк (D1).

## 5. Безопасность

| Угроза | Защита | Инвариант |
|---|---|---|
| Ключ `rw` на `pub/` делает `pub/x → secret/y` и публикует чужое | при создании префикс покрывает и путь, и цель | 6 |
| Ключ с префиксом читает через симлинк, созданный админом, файл вне префикса | при каждом чтении через API проверяется **текущий путь цели**; иначе 404 и `target.path = null` | 6 |
| «Отмывание» видимости | эффективная видимость = строжайшая, проверяется на каждом запросе | 2, 3 |
| Раскрытие существования через коды ответа | публичная сторона, сессии и подписанные ссылки — единообразные 404 | 2 |
| Раскрытие через счётчики и пути | `symlinks_affected`, `target`, фильтр `target=` — только в пределах префикса | 6 |
| Запись сквозь симлинк | запрещена (D1) | 6 |
| Web-сессия что-то пишет | `POST /symlinks` — только по API-ключу | 14 |
| Исполнение загруженного HTML через симлинк при включённом sign-in | CSP sandbox по типу содержимого **цели** | 14 |
| Обход проверок подписанной ссылки | порядок §8.2 не меняется: `exp` до БД, затем симлинк + цель | 7 |
| Гонки переименования | резолв по ID в одном чтении; путь цели в этот момент не важен | — |
| Перебор рекурсивным созданием | одна транзакция + лимит D10; JSON-тело ограничено | 8 |
| nginx принимает решения о доступе | нет: velad резолвит, nginx получает только `X-Accel-Redirect` на блоб цели | — |

## 6. Отдача содержимого (SPEC §11.3)

- Для доставки симлинк подменяется копией, у которой блоб, размер, SHA-256 и тип — от цели, видимость —
  эффективная, срок жизни — ближайший из двух.
- ETag = `"sha256:<hex цели>"`: тот же байтовый поток — тот же валидатор; перезапись цели меняет ETag.
- `Cache-Control` — по эффективной видимости.
- `Content-Disposition`: имя файла — имя **симлинка**, `disposition` — симлинка.
- Accel: `X-Accel-Redirect` на блоб цели; заголовки ровно по разу, внутренние не утекают (инвариант 13).
- R2: presigned-grant с именем и `disposition` симлинка.
- `noindex` — по директории симлинка.

## 7. Хранилище

Миграция `0006_symlinks.sql` пересобирает `objects` и `trash` (SQLite не умеет снять `NOT NULL`):

- новые колонки `kind TEXT NOT NULL DEFAULT 'file' CHECK (kind IN ('file','symlink'))` и `target_id TEXT`;
- `blob_id` — nullable, `UNIQUE` остаётся (несколько NULL не конфликтуют);
- `CHECK ((kind = 'file' AND blob_id IS NOT NULL AND target_id IS NULL) OR (kind = 'symlink' AND blob_id IS NULL AND target_id IS NOT NULL))`;
- у симлинков в строке хранятся `size = 0`, `sha256 = ''`, `content_type = ''`;
- индекс `objects_target_id` по `target_id`;
- все индексы `objects` и `trash` пересоздаются.

Запросы объектов присоединяют цель (`LEFT JOIN objects t ON t.id = o.target_id`) и запись корзины цели;
эффективная видимость и «живость» для листингов, индекса и статистики директорий считаются в SQL.
Все пути, работающие с блобами (сборщик, `BlobReferenced`, purge, backup, сиротские блобы), пропускают
симлинки.

## 8. CLI

### 8.1 `vela ln`

```
vela ln SOURCE DEST                      # один файл
vela ln SOURCE... DIR/                   # несколько: DEST обязан кончаться на "/"
vela ln -r SOURCE_DIR/ DEST_DIR/         # рекурсивно, одна транзакция на сервере
```

- `DEST/` → `DEST/<basename SOURCE>`.
- Флаги: `-f, --force` (D2); `--no-copy-meta`; `--copy-meta` (при перенаправлении); метаданные как у `put`
  (`--public|--unlisted|--private`, `--title`, `--description`, `--tag` (D4), `--disposition`, `--expires`);
  `--dry-run`; `-s, --symbolic` принимается и ничего не делает (скрытый).
- Вывод: `sorted/travel/a.jpg -> originals/a.jpg` + публичный URL (или подсказка `share`); предупреждение,
  если эффективная видимость строже сохранённой.
- `--json`: `Object`, массив `Object` или ответ рекурсивного создания.
- Несколько источников — по запросу на источник; частичный провал → код выхода 7.
- Сервер без `features.symlinks` → понятная ошибка про обновление velad.
- `-r --skip` / `--skip-explicitly` / `--skip-symlinks` → `skip_conflicts` / `skip_conflicts` с выводом каждого
  пропуска / `skip_symlinks`; без `features.symlink_tree_skip` CLI ничего не отправляет и просит обновить velad.
  `--dry-run` учитывает `--skip-symlinks` и вложенный `DEST`, но не проверяет конфликты.
- `-r --sync` планируется на клиенте как `ln --by-tag --sync` (SPEC §12.4.1): выбраны все файлы под `SOURCE`,
  структура сохраняется, симлинки не выбираются, вложенный `DEST` не обходится. Принимает `--prune`,
  `--prune-trashed`, `--strict`, `--copy-meta`, `--skip`, `--skip-explicitly`, `-y`, `--dry-run`;
  `--save-structure` → ошибка использования. Не одна транзакция. `--prune` никогда не трогает симлинки на файлы
  вне `SOURCE`: без тегов нельзя отличить вынесенный файл от связанного вручную; симлинки на файлы внутри
  вложенного `DEST` тоже не трогаются.

### 8.2 Изменения существующих команд

| Команда | Изменение |
|---|---|
| `ls -l` | маркер типа `l`, `name -> target.path`, битые — с `(broken: trashed/gone)` |
| `ls` | флаги `--type file\|symlink`, `--broken`, `--target PATH` |
| `stat` / `meta` | блок Target; для файла — «Symlinks: N» и до 10 путей |
| `rm` | предупреждение по `symlinks_affected`; режим `--broken [-r] DIR/` |
| `trash ls` / `trash purge` | маркер симлинка; предупреждение по `symlinks_affected` |
| `get -r` | пропускает битые с предупреждением → код 7 |
| `put` / `new` | на путь симлинка — понятная ошибка `is a symlink` |

Новых кодов выхода нет.

## 9. Вне скоупа

- Режим «по пути» (аддитивно через `"mode": "path"`).

- `vela cp` (копия с общим блобом).
- Живое наследование метаданных.
- Импорт локальных симлинков в `vela put -r`.

## 10. Тесты (MUST)

- Миграция 5 → 6 на заполненной БД, `CHECK`-ограничения, `PRAGMA integrity_check`.
- Листинг с эффективной видимостью и фильтрами `kind`/`broken`/`target`.
- Матрица §3.3 для четырёх каналов: публичный, web-сессия, подписанная ссылка, API.
- Матрица §3.5: перезапись, move, trash, restore на другой путь, purge, expiry.
- Ключ с префиксом не может ни создать, ни прочитать симлинк на цель вне префикса.
- `is_symlink`, запрет `content_type` в PATCH, `symlinks_affected` в пределах префикса.
- Доставка: ETag цели, имя симлинка в `Content-Disposition`, кэш по эффективной видимости, CSP по типу
  цели, Range, HEAD, 304; e2e через nginx в accel-режиме.
